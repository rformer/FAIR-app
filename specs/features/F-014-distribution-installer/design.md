# F-014 Distribution, installer & licensing — Design
Status: Approved | Requirements version: 2026-11-26 (Approved; OQ1 to OQ17 resolved as proposed) | Last updated: 2026-11-26
Requirements: `requirements.md` · ADR-005, ADR-006, ADR-011, ADR-012, ADR-016, ADR-018 · F-012 (release artifacts), F-015 (deployment checks, exceptions, seed, consent)

## 1. Overview
F-014 turns F-012's signed release into something a customer installs, upgrades, backs up, restores and removes inside their own boundary, with the same rules F-015 applies to the running deployment.
- **One render, three consumers** (R-01). `internal/fleet` already renders `deploy/k8s` into the signed per-release artifact Flux reconciles (F-012 T-15). F-014 adds a second output of the same render: the `fair-platform` Helm chart, whose templates are the rendered objects with only the instance values and the dependency switches templated, under a closed values schema. A chart can therefore not loosen the reference hardening, and a test holds chart and fleet artifact equal. The chart is published as a signed OCI artifact; the air-gap package is a Zarf package plus the verification kit beside it (OQ1).
- **Bundled or brought, per dependency** (ADR-005's table). The chart carries optional, equally hardened components for PostgreSQL (CloudNativePG with our FIPS PostgreSQL image), NATS JetStream, the object store (versitygw, ADR-020), Keycloak, OpenBao and the OpenTelemetry Collector. Every bundled image the package holds is signed with the release key and attested like the platform's.
- **`fairctl`, the installer** (R-02, OQ2). One Go command built with the FIPS module for Linux, macOS and Windows: `verify`, `preflight`, `install`, `upgrade`, `rollback`, `backup`, `restore`, `license`, `uninstall`, `decommission`, `report`. It verifies the release offline with the release key alone (standard library, no cosign), asks for or reads every install-time decision, generates every credential into the mode's key store, provisions what the services refuse to create, and installs through the chart with the Helm SDK (ADR-019). It is resumable: every step is idempotent and recorded.
- **Preflight is F-015's check catalog, plus what only exists before install** (R-03). `internal/preflight` runs `internal/scanner/checks` (the same functions, not a copy) over an overlay of the live cluster and the objects the release would apply, so a configuration preflight accepts is exactly one drift accepts (AC-18, `TestPreflightMatchesDrift`). Preflight-only checks cover the cluster (version, network plugin, admission, clocks, egress) and the dependencies (PostgreSQL, key store, stores, NATS, capacity). Hard-floor failures (ADR-006 amendment 1) have no override; any other failure proceeds only on a named override, which becomes an expiring **deployment exception** on the Posture page and in the POA&M (OQ5).
- **Licences are signed files, verified offline, that never touch security** (R-04). A `fair.license-file.v1` document signed by a dedicated KMS key (ADR-021), verified against public keys embedded in the release, bound to the installation identifier the first licence brings (OQ6). After the end date and 30 days' grace the platform enters a limited state that refuses only the creations OQ9 lists, through one gate whose list a test proves contains no security route (AC-24).
- **Upgrades go forward only, from the window F-012 tests** (R-05). Two previous minor releases (any patch), never a downgrade; verify, preflight, entitlement and a verified backup no older than 24 hours first; writes paused only for migrations; rollback to the previous images (expand–contract, F-012-AC-21).
- **Backups the customer holds the key to, restores proven before use** (R-06, ADR-022). Point-in-time PostgreSQL (WAL archiving and base backups for the bundled database), object copies that keep retention and holds, key store snapshots kept apart; AES-256-GCM under the customer's backup key, a signed manifest; a restore stays closed until consistency, posture MACs, a full audit verification and every referenced object's digest pass. A restore to an earlier point records a **declared gap** that the external checkpoint copies prove (OQ13, ADR-011 amendment).
- **The component definition and the responsibility matrix are release artifacts** (R-07). `releasegen component-definition` already builds the OSCAL document from `compliance/statements/`; F-014 makes the gate refuse drafts and missing features, adds the dependencies' shared responsibilities (OQ17) and publishes the matrix as accessible HTML, tagged PDF, CSV and JSON. Exports reference the component definition by version and digest (AC-46).
- **Uninstall keeps, decommissioning destroys only deliberately** (R-08), and **the documentation ships in the package** as an offline, accessible site (R-09). Installer output is plain text with a JSON equivalent and documented exit codes; the application shows install, licence, backup and preflight status on the Posture page (R-10).

## 3. Design
### 3.1 The chart and the air-gap package (AC-01, AC-02, AC-04, AC-05)
- **Chart.** `oci://ghcr.io/rformer/charts/fair-platform:<version>`, pushed by `publish` after the gate, signed keylessly and with the release key on its OCI digest like the images (`cosign sign`, F-012 design §3.3). `Chart.yaml` annotates the release manifest's digest; every image is named `repository@sha256:…` from the manifest, so whichever registry the administrator mirrors to, the digests are the signed ones (AC-04). The values select a registry prefix (`global.registry`), never a tag.
- **Air-gap package** (`fair-<version>-airgap.tar`), one directory:
  - `zarf-package-fair-platform-<arch>-<version>.tar.zst`: the chart, every image any option can run (platform, bundled third parties, `fairctl`), and their cosign signature and attestation artifacts as OCI referrers, in Zarf's OCI image layout;
  - the verification kit, readable without Zarf (OQ1): `release-manifest.json` and `.sig`, `cosign.pub`, `SHA256SUMS` and `.sig`, `package-manifest.json` and `.sig`;
  - `tools/`: `fairctl` and `fair-audit-verify` for Linux, macOS and Windows (amd64, arm64), `releasegen` (for `verify` only);
  - `content/`: the profile packages and their manifest, the shipped frameworks, starter library, question bank and ASN data, as the images embed them (listed so an assessor can read them);
  - `compliance/`: the component definition and the responsibility matrix (§3.13);
  - `docs/`: the offline site (§3.15), `notes/`: the release notes of every release in the upgrade window (§3.10), `platforms.json`: the supported Kubernetes versions and distributions (OQ14).
- **`package-manifest.json`** (`fair.airgap-package.v1`): the release, its source date, the first release date of its minor line (for entitlements, §3.9), the supported upgrade sources, and the SHA-256 of every file and every image digest in the Zarf package; signed with the release key (profilepkg format, `releasegen sign -kms`), and the whole tarball signed keylessly and with the release key (`cosign sign-blob`), so both verify offline with `cosign.pub` (AC-02).
- **Zarf's role is transport.** `zarf package deploy` is not the install path: Zarf (Apache-2.0) mirrors the images into the private registry (`zarf package mirror-resources`), or `fairctl registry load` does the same from the layout through the OCI client the Helm SDK links (D-OQ1); `fairctl` reads Zarf's layout directly (tar and zstd), so verification never depends on the Zarf binary. The Zarf package is also signed with the release key (`zarf package sign`, KMS) for customers who inspect it with Zarf.
- **No outbound connection** (AC-05): nothing in the package names a URL it needs; every content item is embedded; the install matrix (§3.17) installs, upgrades, backs up and restores from the package in a cluster with no egress.

### 3.2 The chart from the reference manifests (AC-03)
- **Missing reference manifests first.** `deploy/k8s` has no `gateway` or `posture` Deployment, although `keys/secret-mounts.yaml` patches both and the fleet renderer patches only Deployments the release has; F-014 adds `deploy/k8s/gateway.yaml` (Deployment, Service, ingress policy, `Ingress` with an OpenShift `Route` variant), `posture.yaml`, the `fair-release-manifest` ConfigMap and `nats-streams.yaml` (the JetStream streams as data for the installer). F-012's fleet artifact picks them up unchanged (§10).
- **`fleet.RenderChart`** shares `Render`'s loading, image substitution and key-mount patching, then writes `templates/` instead of kustomizations:
  - each placeholder of `fleet.Variables` becomes one value (`REPLACE_WITH_DB_HOST` → `{{ .Values.database.host | quote }}`), each `ghcr.io/rformer/fair-<c>:REPLACE_WITH_DIGEST` the manifest's digest under `global.registry`;
  - the key store selects one of two pre-rendered patch sets: Kubernetes Secrets (`secret-mounts.yaml`) or OpenBao sidecars (`keys/openbao/`); the SaaS External Secrets set stays in the fleet artifact only;
  - each bundled dependency's objects are wrapped in `{{- if .Values.<dep>.bundled }}`; brought dependencies take their endpoint, CA and credential file references as values;
  - `values.schema.json` is closed (`additionalProperties: false` everywhere): host names, CIDRs, sizes, storage class, replica counts, the registry, the key store kind, the scanner and fips-probe switches, and the bundled switches; no field reaches a security context, a capability, an image tag or a network policy rule;
  - hooks: `pre-install`/`pre-upgrade` weight −10 runs the in-cluster preflight (`fairctl preflight -in-cluster`, read-only RBAC created and deleted with the hook), weight 0 the existing `iam-migrate` Job (its TTL removed, as the fleet render does). A bare `helm install` thus refuses an insecure cluster too (OQ2), though only `fairctl` provisions keys, roles and decisions: without them the services refuse to start (their `CheckInstall`s), which the chart's `NOTES.txt` says.
- **Equality with the fleet artifact:** `TestChartMatchesFleet` renders the chart with values equal to a fleet instance's variables and compares every object with the fleet artifact's (only the SaaS key-store patches and mode differ).
- **Gate:** §3.17 renders every option combination and runs F-015's checks over the result.

### 3.3 Bundled dependencies (ADR-005's table; OQ3, OQ17)
| Dependency | Bundled | Image | Brought |
|---|---|---|---|
| PostgreSQL 16 | CloudNativePG `Cluster` (3 instances), operator installed namespace-scoped (`WATCH_NAMESPACE=fair-data`) | Ours: PostgreSQL 16 on Debian with OpenSSL 3's FIPS provider at a validated version, `ssl_min_protocol_version=TLSv1.2`, the backup plugin (§3.11) (D-OQ2, D-OQ3) | Managed or own PostgreSQL 16+, preflight-checked (§3.7) |
| NATS JetStream | 3-node StatefulSet, TLS with installation-CA certificates | Rebuilt from source with `GOFIPS140=v1.0.0` | Existing cluster over TLS |
| Object storage | versitygw, POSIX backend with versioning and Object Lock, one replica on an encrypted volume (ADR-020) | Rebuilt from source with the FIPS module | AWS S3 or another store passing `CheckBucket` / `CheckVersioned` |
| Identity | Keycloak with `deploy/keycloak/fair-realm.json` | Keycloak in its FIPS mode (BC-FIPS) | Customer IdP (SAML/OIDC) |
| Keys and secrets | OpenBao (raft, auto-unseal where a KMS or HSM is offered, D-OQ9) | Rebuilt from source with the FIPS module | Vault/OpenBao, or Kubernetes Secrets with etcd encryption |
| Observability | `deploy/observability/collector-selfhosted.yaml` | The mirrored, release-key-signed Collector (F-012 design §3.6) | OTLP or syslog to the customer's tools |
- Every bundled workload passes the same checks as the platform's (non-root, read-only root, capabilities dropped, default deny, restricted pod security); the CloudNativePG operator's CRDs and its cluster-scoped read objects are installed by `fairctl` with cluster administration during install, and the operator holds write rights only in `fair-data` (§10 conflict 4).
- Rebuilt third-party images go through the image matrix (`.github/actions/image`) with their own targets, SBOMs, SLSA provenance and both signatures; their upstream source is pinned by commit and checksum (`deploy/bundled/sources.json`, checked by `pincheck`).
- **Bundled object store choice (ADR-020).** Criteria (OQ3): compliance-mode Object Lock, legal holds, versioning, TLS 1.2+ with FIPS-capable cryptography, a redistributable licence (no AGPL), maintained, rebuildable. versitygw: Apache-2.0; written in Go, so rebuilt with the FIPS module its TLS and SigV4 run in it; its POSIX backend already passes the `internal/objstore` contract tests (compliance retention, no governance bypass, legal holds, version deletes; ADR-012, `scripts/s3-test-server.sh`). Rejected: MinIO (AGPL-3.0, no published images), Garage (AGPL, no Object Lock), Ceph RGW through Rook (privileged OSDs fail restricted pod security; heavy), RustFS (Rust, no FIPS module path), SeaweedFS (Apache-2.0, viable, more components; the fallback). Limits recorded in ADR-020 and the matrix: the lock is enforced by the gateway, not against someone with access to the volume, and the bundled store is a single replica made durable by backups; customers needing hardware WORM or high availability bring their store (D-OQ12). Per-service credentials (audit store, report store, WORM copy) are versitygw accounts limited to their bucket, generated at install (to confirm in T-07).

### 3.4 The installer (AC-07 to AC-14, AC-54)
- **Form (OQ2).** `fairctl`, a Go binary built with `GOFIPS140=v1.0.0`, `-trimpath`, reproducible like the images; for Linux, macOS and Windows, amd64 and arm64; also an image (`fairctl` target, distroless, 65532) for the chart's hooks and the backup jobs. It links the Helm SDK (`helm.sh/helm`, ADR-019) and the existing kube, pgx, objstore and NATS clients; nothing else outside the standard library (`TestSDKLinkedOnlyIntoTools` extended).
- **Steps of `fairctl install`**, each recorded in the ConfigMap `fair-install` (step names and states, never values) and the local install log (`fair-install.log`, JSON lines, no secrets), each idempotent:
  1. `verify` the package (§3.5); 2. read the decisions (interactive prompts, or `-decisions FILE`); 3. `preflight` (§3.7), overrides named on the command line or in the decisions; 4. generate credentials and load the key store (§3.6); 5. bootstrap database roles; 6. create buckets with Object Lock or versioning, JetStream streams; 7. `helm install` (hooks: in-cluster preflight, `iam migrate`); 8. record: deployment mode, licence and installation identifier, MAC key, posture seed, currency, the first IdP and Platform Admin, scanner consent, FIPS evidence and attestations, break-glass; 9. replay the install log's events into the trail; 10. the install report.
- **Resume and removal (AC-12).** `install -resume` continues from the first step not done; a key, a seeded profile or a recorded decision is never produced twice (generation skips existing store entries; `posture seed` and `install.record_decision` refuse a second, different value and accept the same one). `install remove` deletes only what the recorded steps created, and only while the installation is not `open`.
- **Decisions file (AC-14).** `fair.install-decisions.v1` (YAML, strict): mode, profile, currency, IdP (kind, metadata file path, domains), first admin (email, IdP subject), scanner access (grant or decline, with the manifest's SHA-256 the administrator accepted), node FIPS evidence (`probe` or `attest`), attestations (cluster-wide pod security, storage encryption per class), break-glass (off, or a reason and holders), overrides (check, subject, reason), sizes, hosts, the key store and the brought dependencies' endpoints and credential **file paths**. A secret-looking value anywhere (`audit.LooksSecret`, private key or token shapes) refuses the file before anything runs.
- **Install report (AC-13).** `fair.install-report.v1` (release, package digest, every decision and attestation with "attested, not verified", every preflight result and override, what was provisioned, timings), written as text and JSON, stored in `install.report`, shown on the Posture page.
- **Output (AC-54).** Plain lines, one fact per line, no colour unless `-color` (and never with `NO_COLOR`), no cursor movement or spinners; prompts end with the accepted answers; `-output json` prints one JSON document per command (schemas in `docs/formats/fairctl-*.schema.json`). Exit codes: 0 done, 1 refused (verification or a check failed), 2 usage, 3 interrupted (resumable), 4 environment unreachable. `TestFairctlOutput` checks no escape sequences by default and JSON validity.

### 3.5 Release verification in the installer (AC-07)
`internal/releaseverify` does what `scripts/verify-release.sh -offline` does, in Go with the standard library: the manifest's and `SHA256SUMS`' signatures (`profilepkg.VerifySignature`), every file against `SHA256SUMS` and `package-manifest.json`, each image's cosign signature (the simple-signing payload's digest equals the manifest's; ECDSA over its SHA-256 with `cosign.pub`), and its SPDX and SLSA attestations (DSSE envelopes, PAE, same key; the provenance's builder and source as F-012's admission policy requires). An image whose digest, signature or attestation is missing, wrong or signed by another key refuses the package; online installs may additionally check the keyless signature through `cosign` if present, never instead. `TestVerifyMatchesVerifyRelease` runs both verifiers over `scripts/release-fixture.sh`'s release and its tampered variants and requires the same verdicts. Upgrades verify the new package the same way.

### 3.6 Credentials and provisioning (AC-10, AC-11)
- **Generated** by `fairctl` from Go's FIPS-module random source: the database role passwords (`app_migrator`, `app_rw`, `app_engine`, `app_posture`, `app_gateway`, `app_audit`, `app_notify`, `app_integrate`), the `iam keys init` set (F-001 T-41 layout, `internal/keys.Init`), the posture MAC key (generated in Go, passed to `posture.add_mac_key`, replacing the README's database-side `gen_random_bytes`), the posture export signing key (`posture export-key`), the bundled store's per-service credentials, NATS and internal TLS (an installation CA, ECDSA P-256, unless the decisions name the customer's issuer: cert-manager or files), the backup key and the key-escrow key (§3.11), the bundled Keycloak's bootstrap administrator and client secret.
- **Delivered** only to the mode's store: Kubernetes Secrets (`fair-<service>-<dir>`, 0440) or OpenBao KV v2 entries with the policies of `deploy/k8s/keys/openbao`; nothing in values, the Helm release record, ConfigMaps, the report or logs (`TestSTRIDEF014NoSecrets` scans all of them after a kind install). Each installation generates its own; nothing is shipped.
- **Database roles.** `internal/dbbootstrap` runs `db/bootstrap/0001_roles.sql`'s statements from Go over the administrator's connection, sending SCRAM-SHA-256 verifiers computed locally (never the password), then checks every platform role: not superuser, no `BYPASSRLS`, not an owner of platform tables (`TestBootstrapParity` against `scripts/db-bootstrap.sh`). Brought PostgreSQL needs an administrative connection only for this step.
- **Provisioned**, in order: roles, the buckets (`objstore` gains `CreateBucket(lock bool)`; brought stores are checked, and created only when the decisions allow), the JetStream streams of `nats-streams.yaml` (every `scope.Subjects` subject and `posture.setting.changed`), the release manifest ConfigMap, migrations and release content (the hook), `posture.set_deployment_mode`, `posture seed`, the scanner only when access is granted (`posture k8s-access grant|decline`, recording the permission manifest's SHA-256), fips-probe or the `fair-platform.io/fips=attested` labels, the storage-class and pod-security attestations (`checks.AnnotationEncrypted`, `FAIR_PSA_DEFAULT`), `risk currency set`, the first IdP and Platform Admin (`iam bootstrap`, §10), `iam breakglass enable` when chosen.

### 3.7 Preflight (AC-15 to AC-21)
- **Registry.** `preflight.Checks()` = every `checks.Metas()` entry, run by the same `checks.Catalog` functions, plus the preflight-only checks below; each has an identifier, title, controls, remediation and a documentation anchor (`TestPreflightChecksDocumented`, AC-52).
- **Overlay reader.** Before install the platform's objects do not exist; preflight runs the catalog over `objreader.Overlay(live, rendered)`: cluster-scoped and existing objects from the administrator's read-only connection, the release's rendered objects (from the chart with the decisions' values) as if applied. After install the scanner reads the applied objects themselves, so both evaluate the same objects by the same rule. `TestPreflightMatchesDrift`, over each distribution fixture (`internal/scanner/checks/testdata/{kind,openshift,rke2}`), requires the preflight's findings on the fixture without the platform plus the chart to equal the scanner's on the fixture with the chart applied, for pass and fail fixtures (AC-18).
- **Preflight-only cluster checks:** `kubernetes_version` (a supported minor and distribution, `platforms.json`), `network_plugin` (a NetworkPolicy-enforcing plugin recognized by its DaemonSet: Calico, Cilium, Canal, Antrea, OVN-Kubernetes, OpenShift SDN; an active probe pair during install, not in read-only runs, D-OQ6), `admission_policy` (the signature-verifying admission F-015's `signature_admission` reads, overridable for self-hosted per F-012), `secret_store` (the chosen store reachable; Kubernetes Secrets with etcd encryption attested or visible), `clock_skew` (API server, database and stores' `Date` within `audit.max_clock_skew` of the installer and of each other), `no_egress` (air-gapped: the platform namespaces' policies allow no egress beyond the cluster and the brought dependencies, and the install-time probe pod cannot connect out).
- **Dependency checks:** `postgres_version` (16+), `postgres_tls` (verify-full, TLS 1.2+, approved suites, certificate ≥ 30 days), `postgres_fips` (where the profile requires FIPS: `pgcrypto`'s `digest('x', 'md5')` must fail, as OpenSSL refuses MD5 in FIPS mode; managed services may attest), `postgres_roles` (present; none superuser, `BYPASSRLS`, or owner of platform tables), `keystore_access` (reachable; each service's policy reads only its entries; mounted files 0440), `audit_store` (`CheckBucket`: compliance-mode Object Lock), `report_store` (`CheckVersioned`), `worm_copy` (present where F-002 requires it), `nats_tls`, `capacity` (storage classes and quotas against the sizing guide for the decisions' sizes, `FAIR_AUDIT_STORAGE_QUOTA`), and the TLS probe of `tls_endpoints` reused for every dependency endpoint.
- **Hard floor (AC-19).** `preflight.HardFloor(finding)` classifies by finding, not by check: plaintext or TLS below 1.2 on any platform connection; `node_fips` or `postgres_fips` failing under a FedRAMP- or CMMC-derived profile; `audit_store` without compliance-mode Object Lock; `postgres_roles` bypassing RLS or superuser; `plaintext_secrets` or key files readable by others; release verification failing. These refuse with no override in every mode; SaaS allows no override at all (OQ4).
- **Report.** Per failure: check, subject, what was found (never a value that looks secret), controls, remediation, hard floor or not. `fairctl preflight` alone uses read-only access (the scanner's permission set plus database and store reads), installs nothing, and writes the same report (AC-21); its run is recorded in `install.preflight` once the database exists. Performance: checks run concurrently with per-check timeouts; the whole run ≤ 5 minutes (NFR).

### 3.8 Overrides as deployment exceptions (AC-20; OQ5)
- An override names the check, the subject and a reason; `fairctl` records it in the install log, then, once the database exists, in `posture.deployment_exception` through `posture.add_deployment_exception` (owner and approver `iam.installer_user()`, the operator's stated name in the record), with `expires_at` = now + `exception.max_duration` (90 days in every shipped profile), a row MAC like setting exceptions (F-015 T-36), and the event `posture.deployment_exception_created` at high severity.
- The Posture page lists them with the setting exceptions; the POA&M (`posture.BuildPOAM`) gains one item per open deployment exception; Assessment Results report the check as "not satisfied, excepted".
- Renewal only in the application with dual approval (F-001 approvals kind `deployment_exception.renew`, requester holds `settings.change`, approver another holder of `settings.approve`), at most `exception.max_duration` again. At expiry the posture leader asks the scanner's latest result (or, when access was declined, marks it unverified): a still-failing check opens a high finding `deployment_exception_expired`; `fairctl upgrade` refuses while one is expired and failing.
- This is a second exception kind beside F-015's setting exceptions, sharing their lifecycle code (notices at 14, 7, 1 days; MACs; audit); see §10 (F-015 amendment) and D-OQ14.

### 3.9 Licensing (AC-22 to AC-28; OQ6 to OQ9, OQ16)
- **Format** `fair.license-file.v1`, one JSON file: `license` (an object, canonical as `profilepkg.Encode`) and `signature` (base64 ASN.1 DER over its SHA-256, exactly `profilepkg.Sign`'s format) and `key_id` (SHA-256 of the key's SPKI). The licence: `format`, `license_id`, `customer {id, name}`, `installation_id`, `modes` (subset of `saas`, `self-hosted`, `air-gapped`), `not_before`, `not_after`, `updates_until`, optional `named_users` (shown and reported, never enforced, OQ8), `issued_at`.
- **Keys (OQ7, ADR-021).** A dedicated ECDSA P-256 KMS key, separate from the release key, used through a role only vendor licensing may assume; signed with `releasegen sign -any -kms` (ADR-018's signer, so no new SDK). Public keys are embedded in `internal/license/keys/` (covered by the image digests and the signed manifest), each with a "valid for licences issued until" date; a new key ships one release before it signs; an old key stays until every licence it signed has ended.
- **Verification** in every mode, offline, in Go: signature with a shipped key, schema, installation identifier equal to the recorded one (the first licence brings it, `install.installation`), mode permitted, `not_before` reached. Refusals are recorded (`license.refused`) with the reason, never the file. Nothing calls the vendor (AC-22).
- **States**, computed on read from the current licence and the clock: `valid`, `expiring` (≤ 60 days), `grace` (after `not_after`, 30 days), `limited`, and `none` (installs always bring one). A leader job in the posture service records each transition once (`install.license_event`) with its audit event, and queues notices at 60, 30, 14 and 7 days and at grace and limited (`install.notice_outbox`, F-009 source `install`) to Platform Admins (AC-25, AC-28).
- **Installing** a licence: `fairctl license install FILE` (cluster access) or `PUT /api/v1/posture/license` (`license.manage`, reason): verified, stored, applied at once; services read `install.license_state()` with a 60-second cache and a `posture.setting.changed`-style NATS nudge (`install.license.changed`), so no restart (AC-27).
- **Limited state (OQ9).** `license.Gate` (in `internal/server` middleware for the risk and integrate services) refuses with 409 `license_limited` exactly: new simulation runs and reproductions; creating scenarios, library entries, controls and register risks; imports and connector runs; new report schedules. Everything else continues, including new versions of existing items and the register's exposure aggregates and roll-ups (D-OQ5). `TestLicenseNeverGatesSecurity` reads every OpenAPI contract and requires the gated operations to be exactly that list, none of them in the iam, gateway, posture, audit or notify services and none tagged with a security event (AC-24). The licence never reads or writes a setting.
- **SaaS (OQ16):** onboarding issues the instance's licence for the contract term; the fleet renews it; the same code verifies it (§3.18).

### 3.10 Upgrades (AC-29 to AC-34; OQ10)
- **Window.** `package-manifest.json` lists the supported sources: every patch of the two previous minor releases, and earlier patches of the same minor (F-012 OQ9; ADR-005 amended, §10). `fairctl upgrade` refuses another source naming the release to upgrade to first, and refuses a downgrade (AC-29).
- **Before changing anything (AC-30, AC-32):** verify the package (§3.5); run its preflight; check the licence's entitlement (the release's minor line first released on or before `updates_until`, or a patch of such a minor); require a verified backup no older than 24 hours or take one (§3.11); refuse while a deployment exception is expired and failing; show the notes of every crossed release from `notes/` (migrations, settings packages, permission catalog, scanner permissions, security fixes; F-012-AC-12), the active profile package's changes (`iam migrate -plan`: pending migrations and `posture.sync_packages`' diff without applying), and the expected interruption.
- **Applying (AC-31):** `install.state` becomes `upgrading` (mutations answer 503 `upgrading` with `Retry-After`; reads continue); roles re-asserted (`internal/dbbootstrap`), `iam keys upgrade` on the store's copy, new buckets and streams, `helm upgrade` (hooks: preflight, migrations); the scanner's permission manifest's SHA-256 compared with the recorded consent, asked again before the new services start when it changed; `install.state` back to `open`. Writes pause only while migrations run (target ≤ 15 minutes at target scale, measured by the upgrade test's timing at bench scale).
- **Rollback (AC-33):** `fairctl rollback` = `helm rollback` to the previous release's images on the upgraded schema (expand–contract, `TestUpgradeFromPreviousReleases`); the schema before the upgrade comes back only by restore.
- **Records (AC-34):** `install.upgrade_started`, `install.upgrade_completed`, `install.upgrade_failed`, `install.rolled_back` with both releases (`install.release` rows); the trail verifies across it (the upgrade test already checks a full verification).

### 3.11 Backup and restore (AC-35 to AC-42; OQ11, OQ12; ADR-022)
- **What and how.** A backup is a set at one recorded point in time *T*:
  - **PostgreSQL, bundled:** continuous WAL archiving and scheduled base backups through `cmd/pgbackup`, a CloudNativePG plugin (CNPG-I) that encrypts each WAL segment and base-backup stream and writes it to the backup destination (D-OQ2); point-in-time recovery to *T*. **Brought:** the customer's own PITR backups to documented requirements; `fairctl` records *T* and verifies restores the same way (OQ11).
  - **Object stores:** for each of the audit store, the WORM copy and the report store, a listing of every version written up to *T* (key, version, SHA-256, retain-until, legal hold) and the objects themselves, copied into the backup. Stores are append-only and versioned, and the database is their index, so the database at *T* plus the versions up to *T* restore consistently.
  - **Configuration:** the decisions, the current licence, the install report, `platforms.json` of the release.
  - **Keys, never inside a data backup:** the key store's own snapshot (OpenBao raft snapshot, or for Kubernetes Secrets `fairctl backup keys`), encrypted under the separate key-escrow key and written to a different destination (AC-36, OQ12).
  - JetStream is not backed up; restore re-provisions the streams (OQ11).
- **Format** `fair.backup.v1`: a manifest (set id, installation id, *T*, components, each chunk's SHA-256, the store listings, the release), signed with the installation's backup signing key (ECDSA P-256, generated at install, public half recorded in `install.installation`); chunks AES-256-GCM (FIPS module) under per-set data keys wrapped with the customer's backup key, a file delivered by the mode's store only to the backup jobs (KMS or HSM through the store's delivery, D-OQ9). Destinations: an S3 bucket (`objstore`), or a filesystem path, including removable media (`fairctl backup run -to DIR`).
- **Schedules and records.** `fairctl backup schedule` creates the `fair-backup` CronJob (image `fairctl`, the backup key and the migrator's read connection only); each set is recorded in `install.backup` and verified after writing (manifest signature, every chunk read back and digested). The posture drift engine's new check `backup_freshness` opens a high finding when the newest verified set is older than `backup.max_age_hours` or the last scheduled run failed, and notifies Platform Admins (AC-41).
- **Restore** (`fairctl restore -backup ID [-target-time T] [-new-cluster]`): verify the manifest's signature before reading anything; restore keys from the key snapshot into the (new) store; PostgreSQL to *T*; objects re-put with their recorded retain-until (never shorter; compliance mode refuses shortening anyway) and legal holds; the version identifiers the stores give are mapped back in the database through `audit.restore_versions` and `report.restore_versions` (definer functions, audited); streams re-provisioned; `install.state` = `restoring` from the first step, so every service answers 503 `installation_closed` except health.
- **Verification before use (AC-38):** `amcheck` (`bt_index_check` on every platform index) and the manifest's row counts; `posture.mac_mismatches()` empty; a full audit verification including archives and WORM copies (`audit verify -once -full`, the Verifier's full run as a one-shot command); every object the database references (`audit.archive`, report files, evidence exports) present with its recorded digest. Any failure keeps the installation closed with the report; success records `restore.verified` and opens it. The same installation identifier, licence and keys hold on a new cluster (AC-40).
- **Drill (AC-42):** `docs/operations/restore-drill.md` and `fair.restore-drill.v1` records in `docs/operations/drills/`; the install matrix backs up and restores bundled and brought installations and runs the AC-38 checks.

### 3.12 The audit trail across a restore (AC-39; OQ13)
- After restoring to *T*, checkpoints after the restored head may exist outside the platform (WORM copies, the SIEM). Today the full verification would report those copies as failures.
- On restore, `fairctl` lists the WORM copies after the restored head, verifies their signatures and that they chain from the restored head (the first lost checkpoint's previous-checkpoint hash equals the restored head's), and records `audit.restore_gap` (restored head segment and sequence, the lost segments' range and last sequence, their statements' digests) through `audit.declare_restore_gap`, with the event `audit.restore_gap_declared` (high).
- The sequencer and checkpointer resume after the highest lost sequence and segment, so no number is used twice and the SIEM's records stay distinguishable; the first new checkpoint links to the restored head with the gap row's hash.
- The Verifier and `fair-audit-verify` accept a gap only when a gap row covers it and its external copies verify and chain; anything else stays a failure (tampering remains detectable). ADR-011 and F-002's design are amended (§10, D-OQ15).

### 3.13 Component definition and responsibility matrix (AC-43 to AC-46; OQ17)

It will refuse a `draft` status, and `profilegen release-check` will refuse a release in which an approved feature (requirements status Approved or later, `specs/features/F-*/requirements.md`) has no statements file, apart from features without implemented tasks.
- **Dependencies (OQ17).** `compliance/dependencies.yaml` (checked like the statements): per bundled dependency and control, the shared responsibility per mode and its hardening guidance; they appear in the matrix, not as components.
- **Matrix (AC-45).** `releasegen responsibility-matrix`: per control and mode, provider, customer or both and the customer's part, as an accessible HTML page (part of the docs site), a tagged PDF/UA-1 through `internal/report` (F-010's writer), CSV and JSON (`fair.responsibility-matrix.v1`); in the GitHub release, `SHA256SUMS` and the package (`compliance/`).
- **Exports (AC-46).** `install.release` records the running release's component definition digest; the Assessment Results and POA&M back-matter resource for the component definition gains the release version and an `rlinks` hash, so each export resolves to a published document.

### 3.14 Uninstall and decommissioning (AC-47 to AC-50)
- `fairctl uninstall`: `helm uninstall` plus the objects `fairctl` created in the cluster (hook RBAC, labels and annotations it attested are left with a note); keeps the database, stores, keys and backups and reports each (AC-47).
- `fairctl decommission export`: records `install.decommission_started`, runs the whole-root risk export (`fair.risk.v1`, F-003), the register, acceptance and treatment reports as JSON and CSV (F-010), and an audit evidence export of the whole trail (F-002-AC-32), each verified (`fair-audit-verify verify-export`, digests), and keeps their digests.
- `fairctl decommission destroy -installation ID -confirm ID`: refuses unless the final export exists and verified; archives every remaining segment (the archiver's `final` run, keeping each `destroy_after`), verifies the archives, then drops the database, deletes store versions that no retention or hold protects, and destroys the keys last, keeping the public keys needed to verify what remains (checkpoint keys, export key, backup signing key). Audit records within total retention or under hold are never destroyed: WORM objects stay locked and listed (AC-49).
- The **decommissioning record** `fair.decommission-record.v1` (what was destroyed and when, what is kept and until when, the final exports' digests, the kept public keys), signed with the export signing key before it is destroyed (AC-50).

## 4. Settings and permissions
- **Settings (F-015).** One: `backup.max_age_hours` (int, lower is stricter, default 24, bound 168, not BU-scopable, controls CP-9, CP-10), registered by the posture service; packages 1.11.0 with 60 settings (D-OQ10). ## 5. Data model
Schema `install`, owned through the bootstrap role `install_definer` (re-run `scripts/db-bootstrap.sh`); every table definer-only, read and written through functions; no BU-owned tables and no risk data. `fairctl` writes as `app_migrator` (as `iam migrate` and `iam keys register` do).
| Table | Purpose | Rules |
|---|---|---|
| `install.installation` | Singleton: installation id, customer id, mode, state (`installing`, `open`, `upgrading`, `restoring`, `closed`, `decommissioning`), reason, since; backup signing public key | State moves only by functions (PF035) |
| `install.decision` | key, value, attested, reason, operator, recorded at | Append-only; a second, different value refused (PF035) |
| `install.release` | release, manifest, package and component definition digests, kind (`install`, `upgrade`, `rollback`, `restore`), started, finished, outcome | Append-only |
| `install.preflight` | run id, release, purpose, started, finished, result, report (no secrets), digest | Append-only |
| `install.report` | the install report per release row | Append-only |
| `install.license` | licence id, document, signature, key id, installed at and by, superseded at | Append-only but `superseded_at` |
| `install.license_event` | licence id, kind (notice thresholds, `grace`, `limited`, `limited_ended`, `ended`), at | Unique per licence and kind |
| `install.backup` | set id, components, *T*, manifest digest, destination label (no credentials), state, verified at, result | Append-only but state |
| `install.restore` | restore id, backup set, target time, state, verification report | Append-only but state |
| `install.notice_outbox` | Licence and backup notices for F-009 | As the other outboxes |
| `posture.deployment_exception` | check, subject, finding, reason, operator, owner and approver, created, expires, renewed from, state, row MAC | F-015's exception rules; only posture functions sign |
| `audit.restore_gap` | restore id, restored head (segment, seq, hash), lost range (segments, last seq), external copies' digests | Append-only (PF012) |
Readers: `app_posture` (`install.status()`, licence, backups, preflight, report), `app_rw` and `app_integrate` (`install.state()`, `install.license_state()`), `app_audit` (`install.state()`, the gap). Migrations from 0170: the schema and records; deployment exceptions; licences; backups, restores and the version remapping functions; the restore gap; the notify source `install` (`notify.kind`, `notify.Sources`, `collect`, `recheck`, a noun).

## 7. Security design (STRIDE)
| Threat | Mitigation | Test |
|---|---|---|
| S, T: a tampered, substituted or foreign-key-signed release, chart or package is installed | `fairctl` verifies the manifest, `SHA256SUMS`, `package-manifest.json`, every image's signature and attestations offline with the release key before acting; images by digest; the gate refuses a chart or package that differs from the manifest | `TestSTRIDEF014Verify`, `TestVerifyMatchesVerifyRelease` |
| T: chart values or a bare `helm install` weaken the reference hardening | Templates are the reference render; closed values schema with no security fields; every option combination checked in the gate; in-cluster preflight hook | `TestSTRIDEF014ChartValues`, `TestChartOptionsPassChecks`, `TestChartMatchesFleet` |
| E: preflight accepts what drift would report, or the reverse | One check implementation over the same objects (overlay reader); parity over every distribution fixture | `TestPreflightMatchesDrift` |
| E: an override hides an insecure deployment | Hard floor without override, none in SaaS; overrides named, reasoned, high severity, expiring deployment exceptions in the POA&M; re-checked at expiry; upgrade refuses an expired failing one | `TestSTRIDEF014Overrides` |
| I: generated credentials leak through output, values, Helm records, ConfigMaps, reports or logs | FIPS random source; delivered only to the key store; decisions refuse secrets; SCRAM verifiers to the database; scans after install | `TestSTRIDEF014NoSecrets`, `TestDecisionsRefuseSecrets` |
| S, E: a forged, altered or other installation's licence is accepted, or the licence disables a control | Dedicated KMS licence key; offline verification with embedded keys; installation and mode binding; the gate's list proven free of security routes; the licence never touches settings | `TestSTRIDEF014License`, `TestLicenseNeverGatesSecurity` |
| D: a lapsed licence stops governance or holds data | The limited state refuses only OQ9's creations; sign-in, reads, exports, audit, posture, acceptances, notifications and backups continue; nothing deleted or hidden | `TestLicenseLimitedState` |
| T, D: an upgrade from an unsupported release, a downgrade or a failed migration loses data | Window and downgrade refused; verified backup within 24 hours; expand–contract; rollback to the previous images | `TestSTRIDEF014Upgrade`, `TestUpgradeFromPreviousReleases` |
| I: backups expose data or keys | AES-256-GCM under the customer's backup key; keys only in the separately encrypted key snapshot, never beside the data; destinations without credentials in records | `TestSTRIDEF014BackupConfidentiality` |
| T: an altered backup is restored, or a restore shortens retention or releases holds | Manifest signature and chunk digests before use; retain-until and holds re-applied, never shorter; installation closed until AC-38's checks pass | `TestSTRIDEF014Restore` |
| R, T: a restore is used to disguise deleting audit records | A gap is accepted only with a gap row whose external checkpoint copies verify and chain from the restored head; numbers never reused; any other gap fails | `TestSTRIDEF014RestoreGap` |
| T, R: uninstall or decommissioning destroys retained evidence | Uninstall keeps data; destruction a separate, confirmed step naming the installation; refused within retention or under hold; keys last, public keys kept; signed record | `TestSTRIDEF014Decommission` |
| E: the installer or its hooks leave cluster-wide rights behind | Hook RBAC read-only and deleted with the hook; the running platform holds no cluster-wide write rights; the operator's writes confined to `fair-data`; RBAC hashed in the manifest | `TestSTRIDEF014ClusterRights` |
| I: an air-gapped installation reaches outside | Everything in the package; `no_egress` preflight; CI installs, upgrades and restores with no egress; nothing calls the vendor | `TestSTRIDEF014NoEgress` |

## 10. Changes to other features, ADRs and specs (flagged, not diverged)
1. **ADR-005, upgrade window:** "N-1 → N" conflicts with F-012 OQ9 (two previous minor releases), which OQ10 follows; ADR-005 amendment 2 restates the window (and "rollback via backup/restore" for the schema; images roll back on the upgraded schema).
2. **ADR-005, stale tooling:** its Consequences name Argo CD and Terraform as vendor-ops tooling; ADR-016 chose Flux and OpenTofu. The same amendment corrects it and names the bundled object store (ADR-020).
3. **ADR-005, bundled PostgreSQL:** CloudNativePG is kept, but its operator normally holds cluster-scoped rights, against the NFR "the running platform holds no cluster-wide write rights"; the design installs it namespace-scoped (CRDs and cluster-scoped read objects by `fairctl` at install) and lists the residue in the matrix (D-OQ2).
4. **Reference manifests gap (F-012):** `deploy/k8s` has no `gateway` or `posture` Deployment, so `internal/fleet`'s artifact (F-012 T-15) has none either; F-014 T-04 adds them, which also changes F-012's fleet output.
5. **F-015:** deployment exceptions are a new exception kind (`posture.deployment_exception`), since `posture.exception` is keyed by a setting; preflight runs the scanner's check functions over an overlay reader (`objreader` from the test fixtures); POA&M and Assessment Results gain deployment exceptions and the component definition's digest. F-015's design is amended (D-OQ14).
6. **F-002 and ADR-011:** the Verifier and `fair-audit-verify` today fail on WORM copies past the trail's head; a declared restore gap (§3.12) is an amendment, as are the one-shot `audit verify -once -full`, the archiver's `final` run, and `audit.restore_versions` for remapped object versions (D-OQ15).
7. **F-010:** `report.restore_versions` for the report store's remapped versions.
8. **F-001:** catalog version 8 (`license.manage`); an install-time `iam bootstrap idp|admin` (the first IdP and Platform Admin while nobody has signed in; today only `iam.bootstrap_platform_admin(u)` for an existing user exists) (D-OQ8).
9. **F-012:** onboarding and promotion run the preflight with no overrides (OQ4); onboarding issues SaaS licences (OQ16); release jobs `chart`, `package`, the extended gate and `install-matrix.yml`; `required_checks` in `infra/github/variables.tf` gains the PR install job.
10. **ADR-006:** "unless an explicit, logged override is given" now means an expiring deployment exception and never below the hard floor (OQ5); ADR-006 amendment 2 records it.
11. **ADR-018:** a second KMS key (licences) with its own role, signed through the same `releasegen sign -kms` (amendment).

13. **README:** the posture MAC key is generated in Go by the installer, not by `gen_random_bytes` in the database (AC-10's FIPS module).

## 11. Deployment modes
| Concern | SaaS | Self-hosted | Air-gapped |
|---|---|---|---|
| Artifact | Fleet artifact (same render) | Chart from the registry, or the package | Package only, into a private registry |
| Verification | Admission (F-012) | `fairctl verify` online or offline | `fairctl verify` offline |
| Preflight | Onboarding and promotion, no overrides | Install and upgrade; overrides above the floor | Same, plus `no_egress` |
| Key store | Cloud secret manager (F-012) | OpenBao/Vault or Kubernetes Secrets | Kubernetes Secrets or bundled OpenBao |
| Licence | Issued at onboarding, renewed by the fleet | Signed file | Signed file |
| Backups | F-012's (CP-9) | `fairctl backup` or the brought dependency's own | Same, to customer media |
| Bundled dependencies | None | Optional each | Optional each |

## 12. Alternatives considered
- **A hand-written Helm chart:** two sources of the hardening to keep equal; the generated chart has one (§3.2).
- **A Kubernetes operator or web installer:** out of scope for v1 (OQ2); an operator would hold standing cluster rights.
- **Shelling out to `helm` and `cosign`:** neither is built with the FIPS module, and verification would depend on tools the customer must trust separately; `fairctl` links the Helm SDK (tools only) and verifies with the standard library (ADR-019).
- **`zarf package deploy` as the installer:** Zarf would own the install flow, without decisions, key generation or the preflight's floor; Zarf stays transport.
- **Online licence checks or feature editions:** rejected (A7, ADR-006, OQ8).
- **`pg_dump` backups:** no point-in-time recovery and long restores at target scale; CloudNativePG's barman-cloud: no client-side encryption under a customer key with FIPS cryptography (ADR-022).

## 13. New ADRs (proposed with this design)
- **ADR-019 Self-hosted distribution and installer:** the chart generated from the fleet render; OCI chart and Zarf package with the verification kit beside it; `fairctl` in Go with the FIPS module, the Helm SDK linked into tools only, release verification with the standard library; the docs renderer as a build-only dependency.
- **ADR-020 Bundled object store: versitygw**, rebuilt from source with the FIPS module, with the criteria, the candidates weighed and its limits.
- **ADR-021 Licences:** `fair.license-file.v1`, the dedicated KMS key and its rotation, offline verification, the limited state.
- **ADR-022 Backup and restore:** point-in-time PostgreSQL through our CloudNativePG plugin, object copies keeping retention, separate key snapshots, AES-256-GCM under the customer's key, the restore gap.
- **Amendments:** ADR-005 (upgrade window, tooling, bundled store), ADR-006 (overrides as expiring exceptions), ADR-011 (declared restore gaps), ADR-018 (the licence key).

## 14. Risks & open questions
- D-OQ1 (resolved 2026-11-26: as proposed): How does `fairctl` install? Proposed: the Helm SDK (the newest release at least two weeks old when T-06 starts), linked only into `fairctl` and `releasegen`/`profilegen` (render), using its OCI client for registry loads; no `helm` or `cosign` binary required.
- D-OQ2 (resolved 2026-11-26: as proposed): Bundled PostgreSQL: CloudNativePG (ADR-005) or a plain StatefulSet? Proposed: CloudNativePG, operator namespace-scoped, our FIPS PostgreSQL image, backups through our CNPG-I plugin (`cmd/pgbackup`); if CNPG-I cannot carry encrypted WAL archiving in T-25, fall back to an `archive_command` tool in our image and record the change in ADR-022.
- D-OQ3 (resolved 2026-11-26: as proposed): FIPS for bundled third parties? Proposed: rebuild NATS, OpenBao and versitygw from pinned source with `GOFIPS140=v1.0.0`; PostgreSQL with OpenSSL 3's FIPS provider at a validated version (self-test at start); Keycloak in its documented FIPS mode with BC-FIPS; the CloudNativePG operator (no data-path cryptography of its own beyond the API client) mirrored and re-signed (F-012 design §3.6 amendment).
- D-OQ4 (resolved 2026-11-26: as proposed): Images once or twice in the package? Proposed: once, in Zarf's OCI layout, which `fairctl` reads directly.
- D-OQ5 (resolved 2026-11-26: as proposed): In the limited state, are new versions of existing items and register aggregates allowed? Proposed: yes; only the creations OQ9 lists are refused, so governance and evidence never stop.
- D-OQ6 (resolved 2026-11-26: as proposed): Network plugin enforcement in a read-only preflight? Proposed: recognition by DaemonSet and its policy support in read-only runs; an active probe pair (deny then allow) only during install.
- D-OQ7 (resolved 2026-11-26: as proposed): OpenShift in CI? Proposed: MicroShift on a larger runner with nested virtualization for every nightly and release run; OpenShift Local or OKD as a recorded run per minor release.
- D-OQ8 (resolved 2026-11-26: as proposed): The first IdP and Platform Admin at install? Proposed: `iam bootstrap idp` (SAML metadata or OIDC discovery file, or the bundled Keycloak) and `iam bootstrap admin -idp NAME -subject S -email E`, allowed only while nobody has signed in, creating the user bound to that IdP subject and calling `iam.bootstrap_platform_admin`; never linking by email (F-001 addition).
- D-OQ9 (resolved 2026-11-26: as proposed): OpenBao unseal material and the backup key's custody? Proposed: auto-unseal through the customer's KMS or HSM (PKCS#11) where offered; otherwise Shamir shares written as 0600 files to custodian paths the decisions name (removable media), never printed; the backup and key-escrow keys are files delivered by the store, with KMS/HSM custody through the store's delivery.
- D-OQ10 (resolved 2026-11-26: as proposed): Backup freshness as a posture setting? Proposed: yes, `backup.max_age_hours` (default 24, bound 168), so loosening it is explicit, audited and visible.
- D-OQ11 (resolved 2026-11-26: as proposed): "Licence" or "license"? Proposed: "licence" in prose (the requirements' spelling), `license` in identifiers (OQ15's permission key).
- D-OQ12 (resolved 2026-11-26: as proposed): The bundled object store's limits (single replica; lock enforced by the gateway, not against volume access)? Proposed: accept for v1, documented in ADR-020, the sizing and hardening guides and the matrix; customers needing hardware WORM or HA bring their store.
- D-OQ13 (resolved 2026-11-26: as proposed): How do services honour a closed or upgrading installation? Proposed: `internal/server` middleware reading `install.state()` (10-second cache and the NATS nudge): closed or restoring answers 503 `installation_closed` to everything but health; upgrading answers 503 `upgrading` to mutations only.
- D-OQ14 (resolved 2026-11-26: as proposed): Deployment exceptions in their own table? Proposed: yes (`posture.deployment_exception`), sharing F-015's lifecycle code and MACs, with owner and approver `iam.installer_user()` at install; F-015's design amended.
- D-OQ15 (resolved 2026-11-26: as proposed): Numbers after a restore to an earlier point? Proposed: the sequencer and checkpointer resume after the highest lost sequence and segment known from the external copies, so nothing is numbered twice; ADR-011 amended.
- Risks: the install matrix's runtime and runner cost (OpenShift needs a larger runner); upstream FIPS builds of third parties may lag their releases; versitygw's maturity at the bundled scale (SeaweedFS is the fallback); recorded manual runs on EKS, AKS and GKE depend on vendor accounts.
