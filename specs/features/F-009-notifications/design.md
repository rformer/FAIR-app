# F-009 Notifications — Design
Status: Approved | Owner: Robert Former | Last updated: 2026-11-16
Requirements: `requirements.md` (Approved 2026-11-16) · ADR-003, ADR-005, ADR-006, ADR-007

## 1. Overview
- **A new service, `notify` (decided 2026-11-16).** It has its own image (`cmd/notify`), its own database role `app_notify` and a bootstrap definer role `notify_definer`. It is the only pod with egress to SMTP relays and webhooks (its NetworkPolicy), so no other service gains outbound access. It serves the notifications API behind the gateway (segment `notifications`).
- **Producers stay as they are (decided 2026-11-16).** `notify.collect()` takes the pending rows of each feature's outbox into one normalized `notify.notice` in a single transaction, and marks them delivered there. The outboxes are `iam`, `posture`, `estimate`, `acceptance`, and two new ones: `register` (stale and overdue, R-06) and posture findings (§3.6).
- **Three stages, each a transaction:**
  1. **Collect:** outbox rows become notices.
  2. **Fan out:** a notice's recipients are resolved and re-checked. Each gets an in-app row, plus one delivery per channel (email, webhooks) the notice is for.
  3. **Deliver:** due deliveries are claimed, sent and settled.

  Stages 1 and 2 run on the service's leader every 10 seconds. Stage 3 runs on every replica, claiming deliveries with `FOR UPDATE SKIP LOCKED`.
- **The in-app list always works.** It needs no channel and no egress, so it is the delivery that every deployment mode has (AC-01, AC-02).
- **Minimal outside the app (R-02).** Emails and webhooks are built from fixed templates over a notice's envelope: kind, time, business unit name and a link. They never carry content beyond that, except titles where the setting allows them and the unit is not restricted.
- **Secrets (decided 2026-11-16).** Webhook signing secrets are generated by the platform, shown once, and stored only as AES-256-GCM ciphertext under a key delivered as a file (`notify/secrets`). SMTP passwords are files the customer delivers (`notify/smtp/`), named in the configuration and never sent through the API.

## 3. Model

### 3.1 Sources and recipients (AC-01; OQ5, OQ6)
| Source (outbox) | Kinds | Recipients | Item (type, BU, link) | Mandatory |
|---|---|---|---|---|
| `estimate.notice_outbox` (F-004) | `assigned`, `reminder` | the estimator | estimate request, its BU, `/estimates/{id}` | yes |
| | `finished`, `closed` | the estimator | same | no |
| `acceptance.notice_outbox` (F-008) | `expiring`, `expired`, `suspended` | the owner and requester (rows name each) | acceptance, its BU, `/acceptances/{id}` | yes |
| | `decision_needed` | approvers who may decide it (as the inbox: `acceptance.approve` at the tier's BU, not the requester or owner), at most 50 | same | yes |
| | `decided` | the requester | same | no |
| `posture.notice_outbox` (F-015) | `setting.exception_expiring`, `setting.exception_reverted`, `setting.revert_failed` | the users and permission holders the row names (at the root) | posture, `/posture` | yes |
| `iam.notice_outbox` (F-001) | `breakglass.login`, `breakglass.emergency_enabled` | holders of `breakglass.manage` at the root | the break-glass account, `/audit?target=…` | yes |
| `posture.finding_outbox` (new, §3.6) | `finding.opened` (high, critical) | holders of `drift.acknowledge` at the root | the finding, `/posture` | yes |
| `register.notice_outbox` (new, §3.7) | `risk.stale`, `risk.action_overdue` | the risk's owner | risk, its BU, `/register/risks/{id}` | no |

- **Permission holders** are resolved through `iam.permission_holders(permission, bu)`, including inherited holders.
- **The 50 cap:** when holders number more than 50, the first 50 by name receive the notice. The notice records how many were left out.
- **A new kind** needs a row in this table and in `notify.kind` (§5), which the release syncs. That row sets the kind's template and whether it is mandatory.

### 3.2 Re-checks (AC-04)
A recipient is re-checked when the in-app row is added and again before each email. The notice is dropped for that recipient, with the reason recorded on the delivery, when:
- the user is not `active` (`inactive`);
- the user no longer holds the permission that made them a recipient (`no_permission`);
- the user no longer sees the item (`not_visible`). Per source, that means:
  - for BU-owned items: the item's resource type is in the user's read scope at its BU (`authz.user_scope.read_bus`);
  - for estimate requests: the user is still addressed on the request (`estimate.addressed`);
  - for posture, break-glass and findings: the user holds `posture.view` at the root.

### 3.3 Envelope and templates (AC-05 to AC-07; OQ2)
- **A notice's envelope:** `{id, kind, at, bu: {id, name}, item: {type, id, link}, title?}`.
  - `title` is taken at collection only when `notification.detail = titles` and the item's BU is not inside a restricted subtree (`iam.restricted_root`).
  - Titles are the item's own name: the risk's title, the scenario's name, or the setting's key.
- **Templates are Go templates per kind**, embedded in the binary: `html/template` for the HTML part, `text/template` for the text part and the subject.
  - Every value is escaped by its template.
  - Header values are Q-encoded, and CR and LF are refused.
  - Links are built from the configured base URL (`FAIR_NOTIFY_BASE_URL`, `https` required) and the item's path, never from data.
- **The banner:** every email ends with the system-use banner's short form (F-001 `iam.banner`), if one is set.
- **The webhook body** is the envelope as JSON, format `fair.notification.v1` (documented in `docs/formats/fair-notification-v1.md`).

### 3.4 Channels (AC-08 to AC-12; OQ1, OQ7, OQ8)
- **The SMTP relay:** one per installation.
  - It has a host, a port, a TLS mode (`implicit` or `starttls`), trust anchors (PEM), a from address, an optional username and a `password_file` name.
  - The name must be a file under `/keys/notify/smtp/`; the API never accepts a password.
  - STARTTLS is required when the mode says so. A server that does not offer it is refused, and the message is never sent in plaintext.
  - TLS 1.2 or later; the certificate is verified against the trust anchors, or the system roots if none are given.
  - Authentication is PLAIN, only inside TLS.
- **Webhooks:** any number. Each has a name, an `https` URL, the notice kinds it takes, and a business unit subtree.
  - A webhook receives a notice only if the notice's BU is inside its subtree.
  - It receives a notice of a restricted unit only if its own BU is that restricted unit or inside it (OQ8).
  - Its secret is 32 random bytes, shown once as `whsec_<base64>`.
- **Signing** follows Standard Webhooks:
  - headers `webhook-id` (the delivery id), `webhook-timestamp` and `webhook-signature: v1,<base64 HMAC-SHA-256(secret, id.timestamp.body)>`;
  - for 24 hours after a rotation, deliveries carry a signature by the old secret as well.
- **The destination guard (SSRF; AC-10; OQ7).** Each delivery:
  - matches the host against `notification.allowed_hosts`, a set of host names and `*.` suffixes (`*` alone: any host); the empty set allows nothing;
  - resolves the host, and refuses loopback, link-local, unspecified, multicast and the cluster's ranges (`FAIR_NOTIFY_CLUSTER_CIDRS`);
  - in air-gapped mode, refuses anything outside private ranges (RFC 1918, RFC 4193);
  - dials the checked address itself;
  - follows no redirects and uses no proxy from the environment;
  - times out after 10 seconds, and reads at most 64 KiB of the response.

  Configuration is checked by the same guard, as far as it can be without sending.
- **Test messages** (AC-11) send a fixed `test` notice through the channel and report the outcome: the TLS version, the server's response or the refusal. A test message is never in-app and never retried.
- **Changes** to a channel are versioned, with `expected_version`. Each needs a reason and is audited (AC-12).

### 3.5 Delivery (AC-13 to AC-16; OQ3)
- **A delivery** is one notice to one recipient by email, or one notice to one webhook.
  - Its id, a UUID, is the `webhook-id` and the email's `Message-ID`, so retries look the same to the receiver.
  - A unique key `(notice, channel, recipient)` makes each delivery once.
- **States:**
  - `pending` → `sending`: claimed, with an attempt token, in its own transaction before the network call;
  - `sent`: the receiver accepted it;
  - back to `pending` with `next_attempt_at`: a retryable failure;
  - `failed`: retries exhausted, or a permanent refusal;
  - `dropped`: the recipient re-check failed.

  A claim older than 2 minutes in `sending` is uncertain. It returns to `pending` and is sent again with the same id (AC-13).
- **Retries** wait 30 seconds, doubling each time, capped at 30 minutes, for up to `notification.retry_hours`.
- **Permanent refusals are not retried:**
  - SMTP 5xx on the recipient;
  - webhook 4xx other than 408 and 429;
  - a refused destination.
- **Channel state** is the last success, the last failure and the backlog. One channel's failures never delay the others.
- **Mandatory notices undelivered (AC-15):**
  - When a delivery of a security kind fails, and no email or webhook delivery of that notice succeeded, the leader opens the high finding `notification_undelivered` through `posture.notification_finding`.
  - The finding resolves when a security notice is next delivered by email or webhook.
  - The notice is always in the app regardless.

### 3.6 Findings as notices (decided 2026-11-16)
- A trigger on `posture.drift_finding` queues `finding.opened` into a new `posture.finding_outbox` when a finding of severity high or critical is inserted. A refreshed finding is not an insert.
- This covers F-002's `audit_integrity` and `audit_capacity` findings, F-015's drift findings and revert failures, and F-009's own `notification_undelivered`.
- That last one cannot loop: it is opened once, and its notice is in-app first.

### 3.7 Stale and overdue (AC-20)
- `register.notice_sweep()` runs on the risk service's leader every 15 minutes, beside the acceptance job. It reads every open risk's status set-based (`register.exposures`, F-008) and its overdue actions (`register.treatment.next_due`).
- `register.notice_state(risk_id, condition)` holds which conditions are active.
- A condition becoming true queues one notice to the owner, and clearing deletes its state row. A notice is sent again only after the condition clears and returns.
- At most 500 risks are handled per sweep, as F-008's job.

### 3.8 Preferences and digests (AC-18, AC-19)
- `notify.preference(user_id, kind, email_muted)`: mandatory kinds cannot be muted (refused, 409 `mandatory`).
- `notify.user_option(user_id, digest, digest_hour)`, where `digest_hour` is 0 to 23 UTC, default 7.
- With the digest on, a user's optional email deliveries wait as `pending` with `digest = true`. At their hour, the leader sends them as one email that lists each notice's envelope, and settles them together. Mandatory notices are never held for a digest.

### 3.9 Retention (AC-17; OQ4)
The leader deletes, daily:
- deliveries older than `notification.log_retention_days`;
- in-app rows and notices older than 180 days;
- the notices no row refers to any more.

## 4. Settings (F-015)
| Key | Kind | Default | Bounds (weakest) | Stricter |
|---|---|---|---|---|
| `notification.detail` | enum | `minimal` | `titles` | `minimal` |
| `notification.allowed_hosts` | set | `[]` (nothing allowed) | `["*"]` (any host) | a subset (`subset_is_stricter`); every host added is a loosening, which needs dual approval (`loosening_needs_approval`) |
| `notification.retry_hours` | int | 24 | 1 to 72 | higher |
| `notification.log_retention_days` | int | 90 | 30 to 365 | higher |

- Packages 1.8.0 (52 settings). Tests use a synthetic 1.9.0 for later releases.
- **The set type (amended 2026-11-16).** F-015's reserved `set` type is implemented for `notification.allowed_hosts`, in Go (`settings.KindSet`, `SubsetIsStricter`), SQL (`posture.check_value`, `posture.compare`; migration 0123) and the package tools, parity-tested as F-015 T-13's.
  - **Values:** sorted, without repeats, at most 64 elements of 1 to 255 bytes each. `*` stands for every element and appears alone.
  - **Strictness:** a proper subset is stricter. A set that adds any element is weaker, even when it also drops one, so replacing a host needs approval too.
  - **Scope:** sets are never BU-scopable, since inclusion is a partial order.
  - **Bounds:** a binding gives a set's bound as `max`, here `["*"]`.

## 5. Data model
Schema `notify`, owned through `notify_definer`. No table is BU-owned; every read and write goes through definer functions that take the user from the signed context.

| Table | Contents | Writes |
|---|---|---|
| `notify.kind` | kind, source, mandatory, security, template; synced by `iam migrate` from the release | release sync |
| `notify.notice` | id, source, source_id, kind, envelope (jsonb), item_type, item_id, bu_id, restricted, recipients (spec), left_out, collected_at | `notify.collect` |
| `notify.inbox` | id, notice_id, user_id, created_at, read_at | fan-out; `notify.mark_read` |
| `notify.channel` | id, kind (`smtp`, `webhook`), name, config (jsonb), bu_id, kinds, secret_ct, previous_ct, previous_until, enabled, version, last_success, last_failure | the channel functions |
| `notify.delivery` | id, notice_id, channel_id, user_id, state, attempts, token, claimed_at, next_attempt_at, digest, outcome, reason, sent_at; unique (notice_id, channel_id, user_id) | fan-out and the delivery functions |
| `notify.preference`, `notify.user_option` | as §3.8 | the user's own functions |
| `register.notice_outbox`, `register.notice_state` | §3.7 | `register.notice_sweep` (register_definer) |
| `posture.finding_outbox` | finding id, severity, check, at, delivered_at | the trigger |

- **Grants:**
  - `notify_definer` gets SELECT and UPDATE (`delivered_at`) on each outbox, from each schema's owner.
  - `app_notify` executes the `notify` functions and nothing else.
  - Application roles cannot reach `notify` tables.
  - Users read their own rows through `notify.my_notifications`, `notify.unread_count` and `notify.mark_read`, keyed on `authz.ctx_user()`.
- **Refusals:** PF028, with the reason as hint.

## 7. Security design (STRIDE)
| Threat | Mitigation | Test |
|---|---|---|
| I: notices leak risk data to email and chat tools | Fixed templates over a minimal envelope; titles only by setting and never for restricted units; webhooks scoped to a BU subtree and restricted units only by their own webhooks | `TestSTRIDEF009Content` |
| I: a notice reaches someone who lost access | Recipients re-checked at fan-out and before each email: active, permission, item visibility | `TestSTRIDEF009Recheck` |
| I, E: a channel used to reach internal systems (SSRF) | Allow-listed hosts; resolved addresses checked, internal ranges always refused, private only when air-gapped; the checked address dialled; no redirects or proxies | `TestSTRIDEF009Destinations` |
| S, T: a forged or replayed webhook delivery | HMAC-SHA-256 over id, timestamp and body with a per-webhook secret; delivery ids stable across retries | `TestSTRIDEF009Signing` |
| I: secrets and credentials disclosed | Webhook secrets shown once, kept as ciphertext under a key file; SMTP passwords are files, never accepted by the API; TLS 1.2 floor with verified certificates | `TestSTRIDEF009Secrets` |
| T: injection through notice content | Template escaping, header encoding, CR/LF refused, links built from the base URL | `TestSTRIDEF009Injection` |
| E: users read others' notices or change channels | Own rows only, by the signed context; channels need notification.manage (privileged) | `TestSTRIDEF009Access` |
| R: configuration changes or failures not attributable | Channel changes, tests, failures, refusals and preference changes audited in their transactions | `TestNotifyAuditEvents` |
| D: a slow or failing channel blocks delivery, or notices flood | Per-delivery claims with SKIP LOCKED; back-off per delivery; timeouts and capped responses; batches; recipient cap | `TestNotifyDelivery`, `TestBenchmarkGateNotifications` |

## 8. New catalog event types
- **Channels:** `notification.channel_created`, `notification.channel_changed` (with what changed), `notification.channel_disabled`, `notification.channel_enabled`, `notification.channel_removed`, `notification.secret_rotated`, `notification.test_sent`.
- **Delivery:** `notification.delivery_failed` (high for security kinds, low otherwise), `notification.destination_refused` (high).
- **Preferences:** `notification.preferences_changed`.

Channels, tests and refusals are category `config`; deliveries and preferences are `system`. Channel and refusal events are severity high.

## 12. Alternatives considered
- **Delivery in the iam worker:** rejected (decided 2026-11-16). The iam pod would gain outbound egress.
- **Producers writing one shared table:** rejected (decided 2026-11-16). It would change every producer, and the outboxes already exist.
- **Admin-supplied webhook secret files:** rejected (decided 2026-11-16). AC-09 generates and shows the secret once.
- **An SMTP or HTTP library:** not needed. The standard library's `net/smtp`, `crypto/tls` (FIPS module) and `net/http` with a custom dialer cover the requirements.
